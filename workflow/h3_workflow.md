# MiniMax H3 实时交互项目工作流

> 适用范围：MiniMax H3/SolarWM-H3 基线、TalkVerse 数据、外部音频条件、AR 与 DMD、FlashHead 实时服务、Agent 接口及评估。  
> 本文件定义稳定执行规则；动态进度统一记录在 [`STATUS.md`](STATUS.md)。

## 1. 项目目标与边界

目标是把 MiniMax H3 的离线原生音画生成能力扩展为可连续运行、可由文本/动作/音频控制、可接入 Agent 的实时交互系统。

当前默认边界：

- 模型基座为 MiniMax H3，SolarWM-H3 是 AR + DMD 的首选训练主线。
- FlashHead 只用于验证实时系统接口，不作为 H3 方法有效性的证据。
- minWM 只提供 Wan 路线的工程经验，不直接证明 H3 代码可复用。
- 首轮参数高效训练只考虑 self-attention Q/K/V/Out LoRA。
- 首轮音频实验从预录音频开始，成功后才进入麦克风实时流。
- 单 A100 优先承担环境验证、推理 smoke、数据处理和小规模实验，不默认承担公开方案的完整多卡训练。

## 2. 事实、测量与推断

每次报告必须区分：

- **事实**：代码、配置、模型 revision、命令、日志或产物可直接核查。
- **测量**：在固定硬件、输入和采样参数下得到的质量、速度和显存结果。
- **推断**：基于事实或测量提出、尚未被当前项目实验验证的判断。
- **未验证**：外部项目声称的能力，或当前环境中没有运行过的能力。

禁止把“仓库已公开”“模型已下载”“单样例成功”分别写成“已部署”“已复现”“已达到实时”。

## 3. 风险等级与授权

| 等级 | 典型工作 | 执行要求 |
| --- | --- | --- |
| L0 | 阅读、盘点、静态检查 | 记录来源，可直接执行 |
| L1 | 文档、测试、局部兼容修改 | 最小修改并做针对性验证 |
| L2 | 数据契约、模型结构、attention mask、指标变更 | 先写实验合同，必须有回归和真实样本 smoke |
| L3 | 下载大权重、多卡训练、长时 GPU 任务、上传发布 | 记录资源预算、恢复方案和用户授权 |
| L4 | 面向用户的实时服务或外部公开演示 | 增加隐私、许可证、内容安全和故障降级检查 |

不得把用户提供的密码、token 或私钥写入仓库、日志、命令文件或实验 manifest。

## 4. 实验状态机

每轮实验只能处于以下一种状态：

```text
DRAFT -> READY -> RUNNING -> PASS | PARTIAL_PASS | FAIL | BLOCKED
```

- `DRAFT`：问题或合同仍不完整。
- `READY`：依赖、资源、输入和验收线均已固定。
- `RUNNING`：任务真实运行中，有进程和日志证据。
- `PASS`：预注册的必需 Gate 全部通过。
- `PARTIAL_PASS`：得到有效信息，但不能进入依赖该结论的下一阶段。
- `FAIL`：假设或实现被证据否定。
- `BLOCKED`：缺少必须由用户或外部条件提供的输入。

失败运行和原始日志不得被同名重跑覆盖；修复后使用新的 `run_id`。

## 5. 实验合同

L2-L4 工作开始前，在正式实验目录创建 `experiment.md`，至少冻结以下内容。

### 5.1 问题与假设

- 本轮只回答什么问题。
- 候选机制为什么可能有效。
- 哪种结果会否定该假设。
- 本轮明确不回答什么。

### 5.2 基线与单一变量

- 基线、候选方案和唯一主要变量。
- 共享的 base checkpoint、adapter 起点和初始化 hash。
- seed、输入提示、音频、分辨率、帧数、采样步数和 CFG。
- 允许改变与必须固定的配置项。

### 5.3 数据契约

- 数据来源、许可、版本、文件清单和 hash。
- train/dev/test 的人物与视频级隔离规则。
- 视频 FPS、音频采样率、时长和精确时间轴。
- video/audio latent 的块边界和映射关系。
- 裁剪、重采样、静音、坏帧、不同步样本的处理。

### 5.4 模型与训练合同

- 仓库 commit、权重 revision 和环境锁文件。
- 可训练参数清单与占总参数比例。
- attention mask、位置编码和 KV cache 语义。
- loss、权重、batch、梯度累积、学习率、步数、精度和 checkpoint 频率。
- GPU 数、显存预算、预计时长和中断恢复策略。

### 5.5 评估合同

- 质量、身份、口型、音画同步、事件一致性、连续性和提示遵循指标。
- 首帧延迟、块延迟、稳定 FPS、峰值显存和长时漂移。
- 人工评测样本数、盲测方式和失败定义。
- PASS 阈值、护栏指标及证据不足条件。

## 6. 项目 Gate

前一层失败时，后一层结果只能用于诊断，不能用来宣称阶段成功。

### Gate 1 — Provenance

确认本地与远程路径、Git commit/diff、模型 revision、环境、GPU、命令、seed、输入 hash、退出码和产物 hash。

### Gate 2 — Environment & Model Load

确认依赖隔离、CUDA/PyTorch 兼容、权重完整、模型可加载，并记录加载时间、峰值显存及 offload/量化状态。

### Gate 3 — Offline Generation

固定输入至少成功生成一次完整视频与音频；验证容器、帧率、采样率、时长、音画轨道和可解码性。

### Gate 4 — Chunk Continuity

验证多块连续生成：边界无明显闪烁、身份突变或音频断裂；记录首块和稳态延迟，不用单块速度代替流式速度。

### Gate 5 — Control Causality

对文本、动作或音频条件做 normal/zero/shuffle/reverse 对照，证明输出变化来自条件，而不是 prompt、seed 或后处理偏差。

### Gate 6 — Distillation & Training Health

检查 loss、梯度、NaN/Inf/OOM、checkpoint 完整性和恢复能力；相同预算比较 Teacher Forcing、AR 与 DMD，短训仅用于排错。

### Gate 7 — Realtime System

验证输入采集、排队、推理、编码和传输的分段延迟；覆盖连续会话、取消、重置、背压、断连恢复和 Agent 指令更新。

### Gate 8 — Long-Horizon & Conclusion

运行预注册时长的长视频，测身份漂移、背景漂移、累计延迟和显存增长；最终结论不得超过已通过 Gate 的证据范围。

## 7. 分阶段执行

### S0：资产与双基线

- 冻结产品 MVP 和统一服务接口。
- 运行 H3/SolarWM-H3 官方推理样例。
- 用 FlashHead 打通实时系统。

退出条件：模型基线和系统基线均为 `PASS`。

### S1：H3 分块交互

- 先使用公开的低步数/AR 权重，不训练。
- 比较基础 H3、SolarWM-H3 和候选加速方案。
- 验证文本或动作逐块更新及连续性。

退出条件：分块控制具有可重复的因果证据，并形成真实硬件性能基线。

### S2：预录音频驱动 PoC

- 方案 A：用 H3 AudioVAE 编码输入音频并 clamp 对应 audio latent，仅预测视频 latent。
- 方案 B：冻结主干并增加轻量音频条件 adapter，仅在方案 A 不足时启用。
- 对照无音频、静音、shuffle 和时间反转条件。

退出条件：口型或音画事件对齐显著优于无条件基线，同时输入音轨未被擅自改写。

### S3：AR 与少步蒸馏

- 复用 SolarWM-H3 的双向适配、Teacher Forcing 和 DMD 流程。
- 在所有阶段保持同一音频条件与 attention contract。
- 比较质量、延迟、显存和长时误差累积。

退出条件：少步模型在预注册质量护栏内获得明确速度收益。

### S4：实时音频与长时记忆

- 加入音频采集、VAD、分块、look-ahead、抖动缓冲和背压。
- 评估 ConvKV 或其他压缩记忆，并与滑动窗口基线比较。
- 接入 Agent 控制和会话状态。

退出条件：长时连续运行没有不可接受的漂移、积压或显存增长。

### S5：冻结与发布

- 冻结代码、权重、数据版本、评测集和结果表。
- 完成许可证、隐私和内容安全审查。
- 只有可追溯结果可进入论文、演示或服务发布。

## 8. 目录与证据

推荐正式实验结构：

```text
experiments/<campaign>/<run_id>/
  experiment.md
  command.sh
  manifest.json
  logs/
  metrics.json
  validation.md
  summary.md
  artifacts/
  run.done
```

规则：

- `tmp/` 只存可删除的下载片段、渲染页、缓存和调试输出。
- 正式合同、日志摘要、指标和小型证据进入 `experiments/`。
- 大权重、数据集和原始视频留在远程存储，仅在 manifest 记录路径、revision 和 hash。
- `run.done` 只有在退出码、产物和必需 Gate 审计通过后才能创建。

## 9. 远程任务规则

- 长任务使用 `tmux` 或 `screen`，固定工作目录、环境和输出目录。
- 启动前检查 GPU、磁盘、进程、权重、数据和输出路径。
- 断线后先检查进程、日志和 checkpoint，不盲目重启。
- 并行任务启动前核算显存、CPU、内存、磁盘与 I/O。
- 不把服务器密码写入脚本；优先使用受控 SSH key 或交互式凭证。
- 未经用户明确要求，不提交、推送、发布模型或启动高成本训练。

## 10. 最终报告格式

每次阶段汇报依次回答：

1. 结论是什么，状态是 `PASS/PARTIAL_PASS/FAIL/BLOCKED` 中的哪一个。
2. 哪些是事实、测量、推断和未验证项。
3. 实际运行了哪些命令和检查，哪些没有运行。
4. 证据、日志和产物在哪里。
5. 最大风险、资源消耗和下一步是什么。
6. 下一步是否需要用户选择、额外资源或授权。

## 11. 总原则

1. 下载成功不等于复现成功，单样例成功不等于实时可用。
2. 一轮实验尽量只改变一个主要因素，并保留公平基线。
3. 音频条件必须通过消融证明因果作用，不能只看主观口型样例。
4. 训练、离线推理和实时服务必须共享同一 token、时间轴和预处理语义。
5. 短训用于排错，不用于替代完整实验结论。
6. 失败日志、异常样例和反例是正式证据，不得静默覆盖。
7. 结论必须追溯到合同、代码、数据、命令、日志、指标和产物。
